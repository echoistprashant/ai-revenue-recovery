# Phase 1 — Core Payment Recovery

## Objective

Build a complete, non-ML recurring-payment recovery baseline that accepts failed payment events, classifies them, applies a fixed retry strategy, records deterministic simulated outcomes, and reports basic metrics.

## Implemented

- Typed payment-event validation with Pydantic
- FastAPI health, ingestion, and metrics routes
- Explicit SQLite schema with foreign keys and unique `(payment_id, attempt_id)` identity
- Nine-category rule-based failure classification
- Fixed retry delays of 1, 6, and 24 hours
- Deterministic simulated baseline outcomes
- Decision, outcome, and audit persistence
- Duplicate-event handling without duplicate actions
- Reproducible synthetic batch generator
- Minimal Streamlit metrics dashboard
- Unit, API, safety, idempotency, and end-to-end batch tests

## Architecture Boundaries

Routes orchestrate the service rather than contain business rules. Classification, baseline selection, persistence, synthetic generation, and API schemas remain separate. No ML scoring or LLM decision path exists.

## Data and Metrics Disclaimer

All Phase 1 outcomes and metrics are generated by a deterministic simulator. They are useful for testing and baseline comparison but are not real payment performance.

## Verification

Using seed `20260827`, the reproducible 200-event baseline produced:

- 200 total failed-payment events
- 180 events with a simulated retry outcome
- 124 simulated recoveries
- 68.89% simulated recovery rate among resolved retry outcomes
- INR 244,276 simulated recovered revenue
- representation across all nine failure categories

The test suite passed 17 tests covering classification, API behavior, idempotency, fraud non-retry behavior, reproducibility, persistence, metrics, and the complete synthetic batch flow.

These values are simulator outputs and are not real commercial results. The final phase report records the Git commit and push status.
